### KB-04 · MAF: timeout, dependencias y correlación

| Campo | Valor |
| --- | --- |
| Versión | 1.0 |
| Sistema | Microsoft Agent Framework (MAF), integración simulada con WorkHub |
| Audiencia | Empleado y soporte L1 del laboratorio |
| Naturaleza | Datos ficticios para simulación; no es una política real del cliente |

#### Alcance y vocabulario

En este laboratorio, «agente MAF» designa un servicio dependiente simulado de WorkHub. El asistente del curso sigue siendo Angular + Express + Claude; no es necesario desplegar Microsoft Agent Framework. Los nombres de operaciones y umbrales siguientes son convenciones del mock, no valores predeterminados del producto.

Un timeout significa que un componente no recibió una respuesta dentro de su plazo. No demuestra que el trabajo remoto se cancelara ni que una operación con efectos no se completase. Puede deberse a una dependencia lenta, cola, red, configuración o ejecución prolongada.

#### Comprobaciones L1

1. Pregunta qué operación se lanzó, cuándo comenzó y si era consulta o escritura. No solicites el contenido confidencial de la petición.
2. Recoge `trace_id` de WorkHub y el identificador de ejecución dependiente si el adaptador lo devuelve. Conserva ambos como campos distintos; solo establece su relación si aparece en los registros.
3. Revisa evidencia autorizada: operación, inicio, duración, resultado y nombre lógico de la dependencia. Un error sin correlación se documenta como evidencia incompleta.
4. En el escenario simulado se puede configurar un plazo de 30 segundos para la llamada dependiente. Si se usa otro, registra el valor efectivo del mock. No lo atribuyas a MAF ni cambies el plazo como solución automática.
5. Si es una lectura, permite un único reintento manual tras comprobar que no hay ejecución activa y registrar el resultado anterior. Si es una escritura, consulta primero su estado o su clave de idempotencia; si no puedes determinarlo, no repitas.
6. Si existe ticket propio, consulta su estado antes de preparar otro. No deduzcas el estado del ticket a partir del fallo técnico.

#### Interpretación y escalado

| Evidencia | Derivación |
| --- | --- |
| Dependencia concreta identificada como lenta | Equipo mantenedor de esa dependencia, mediante soporte |
| Varias ejecuciones afectadas o colas crecientes | Operación de la integración MAF |
| Error solo en WorkHub sin evidencia dependiente | Mantenimiento WorkHub; ver [KB-03](KB-03.md) |
| Ejecución con efectos y resultado desconocido | Escalar sin reintentar; verificar consistencia |

Incluye hora y zona, operación, duración observada, identificadores y número de intentos. L1 no reinicia agentes, cambia modelos, desactiva límites, rota secretos ni modifica infraestructura.

#### Caso de seguimiento

Ante «Estado de mi TCK-501», usa `get_ticket` con la identidad autenticada. Si el servicio autorizado devuelve «En curso», informa de ese estado. La última actualización y el siguiente paso solo se comunican si están presentes en la respuesta; si faltan, dilo. Este artículo explica el diagnóstico MAF y no almacena el propietario ni el estado actual de ningún ticket. Aplica [KB-06](KB-06.md) y [KB-05](KB-05.md).
